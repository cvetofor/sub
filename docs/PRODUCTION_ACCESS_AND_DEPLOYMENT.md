# Production: доступ, выкладка и история

> **Статус:** действует  
> **Актуально на:** 1 ноября 2026 года  
> **Назначение:** понятная инструкция для того, кто поддерживает сайт подписки «Цветофор».

## Что и где находится

- Рабочая копия сайта на production-сервере: `/var/www/cvety`.
- Сайт: `цветы.цветофор.рф`.
- Проект написан на Laravel — это серверная часть сайта на PHP. Админка работает через Filament.
- Ветка `redesign` — исходный код сайта, из неё разрешена выкладка на production.
- Ветка `main` — история утверждённых изменений и постоянные служебные сценарии выкладки.

Разделение важно: выкладка в production принимает только коммиты, которые входят в `redesign`. Перед запуском всегда сверяйте, что нужная правка уже есть в этой ветке.

## Постоянный доступ

Для обычной работы с файлами приложения используется отдельный пользователь `codex-sub`.

- Вход выполняется по личному SSH-ключу, без пароля.
- У пользователя нет прав администратора сервера: он не может выполнять системные команды от имени root и не может менять настройки Nginx.
- Закрытый ключ хранится только у того, кому выдан доступ, и никогда не попадает в репозиторий, переписку или документацию.
- Публичный ключ хранится на сервере в списке разрешённых ключей этого пользователя.

Такого доступа достаточно для чтения и правки файлов сайта, проверки журналов приложения и работы с Git в каталоге сайта. Если требуется изменить Nginx, системные пакеты, пользователей или права доступа, это отдельная административная операция. Она выполняется только после явного согласования и с проверкой результата.

## Как вносить обычную доработку

1. Создать отдельную ветку от актуального кода.
2. Внести изменение и проверить его локально или на сервере под пользователем `codex-sub`.
3. Сохранить изменение в GitHub с ясным описанием: что поменялось, зачем, как проверено.
4. Открыть pull request — предложение объединить изменения в утверждённую ветку.
5. Объединять изменения в `main` только после подтверждения коммерческого директора.
6. Для выкладки открыть GitHub Actions, запустить сценарий **«Выкат коммита redesign на production»**, указать нужную ветку или точный коммит из `redesign`.
7. После выкладки проверить сайт, затронутую функцию и, если менялась админка, вход в неё.

Миграция — это изменение структуры базы данных. Флажок миграций при выкладке включают только если в изменении есть новая миграция и понятно, как откатиться. Для обычных правок интерфейса и текста он не нужен.

## Где хранятся пароли и служебные данные

Пароли, закрытые SSH-ключи и данные для панели хостинга не хранятся:

- в исходном коде;
- в файлах проекта;
- в комментариях и описаниях pull request;
- в документации;
- в сообщениях чата.

Для постоянного сценария выкладки они хранятся только в защищённом хранилище GitHub Secrets. Там доступны лишь названия записей, а не их значения.

После разовых работ временные секреты нужно удалить. На 1 ноября 2026 года удаление трёх временных секретов отложено: GitHub запросил повторное подтверждение входа владельцем аккаунта. До этого момента их нельзя считать удалёнными.

## Важное исправление админки: Livewire и Nginx

31 октября 2026 года форма входа в админку визуально принимала данные, но сбрасывалась. Причина была в Nginx — программе, которая принимает запросы сайта и направляет их в Laravel. Правило для статических JavaScript-файлов перехватывало JavaScript Livewire и возвращало ответ 404 («файл не найден»).

В конфигурации Nginx для сайта перед общим правилом статических файлов добавлен отдельный маршрут:

```nginx
location ^~ /livewire/ {
    try_files $uri /index.php?$query_string;
}
```

Этот блок нужно сохранить при любой полной замене конфигурации Nginx. После изменения конфигурации обязательно сначала выполняют проверку `nginx -t`, затем мягкую перезагрузку Nginx и проверяют страницу входа.

## Проверка после выкладки

Минимальный набор:

1. Главная страница открывается по HTTPS.
2. Если менялся интерфейс — в браузере нет ошибок и загружаются стили и JavaScript.
3. Если менялась админка — вход проходит и открывается «Инфопанель».
4. Если менялась база данных — приложение открывает нужные данные и нет ошибок миграции.
5. В журнале приложения нет новых повторяющихся ошибок.

## Что делать при проблеме

Сначала не меняйте конфигурацию сервера «наугад». Зафиксируйте:

- точное время;
- адрес страницы;
- текст ошибки или снимок экрана;
- что было сделано непосредственно перед ошибкой.

После этого проверьте, какая версия кода сейчас на сервере, и сверяйте её с GitHub. Это позволяет либо исправить проблему в новой ветке, либо безопасно вернуть предыдущую проверенную версию.

# Работа с production-сайтом «цветы.цветофор.рф»

Этот документ описывает **действующий** процесс разработки и выката сайта
подписки на цветы. Он рассчитан на человека, который впервые получил доступ к
репозиторию и должен понять систему, не спрашивая пароли и не заходя в
веб-консоль Beget.

## Главное правило

Код сайта сначала проходит через GitHub, а затем на сервер разворачивается
**тот же конкретный коммит**.

```
рабочая ветка → проверка → redesign → GitHub Actions → production → проверка сайта
```

Не редактируйте файлы сайта вручную на production и не копируйте отдельные
файлы по SSH. Это разрушает соответствие между сервером и GitHub.

## Текущая схема

| Что | Значение |
|---|---|
| Репозиторий | `cvetofor/sub` |
| Рабочая ветка сайта | `redesign` |
| Ветка по умолчанию | `main` |
| Production-домен | `цветы.цветофор.рф` |
| Production-домен, punycode | `xn--b1ag3bn2a.xn--b1ag1aakjpl.xn--p1ai` |
| VPS | `93.189.231.103` |
| Папка сайта | `/var/www/cvety` |
| Удалённый репозиторий сервера | `https://github.com/cvetofor/sub.git` |
| Ветка на сервере | `redesign` |
| Ручной workflow | `.github/workflows/deploy-production.yml` |
| Скрипт выдачи временного ключа | `deploy/beget-prepare.sh` |

Почему workflow лежит в `main`, а сайт — в `redesign`: GitHub показывает
ручной запуск `workflow_dispatch` только для workflow из ветки по умолчанию.
Сам workflow не выкатывает `main`: он получает выбранный SHA из `redesign`
и проверяет его принадлежность этой ветке.

## Кто и какие права имеет

- `codex-sub` — ограниченный пользователь для чтения, аудита и работы с
  исходниками. У него **нет sudo**, доступа к базе, `.env` и рабочим данным
  Laravel.
- `www-data` владеет runtime-папками Laravel: `storage/`,
  `bootstrap/cache/` и собранным фронтендом.
- В обычной работе пароль root и веб-консоль Beget не используются.
- При ручном выкате GitHub Actions через API Beget создаёт новый временный
  Ed25519-ключ с именем `github-actions-cvety`, прикрепляет его к VPS и
  подключается как root только на время данного запуска. Предыдущий ключ с этим
  именем API удаляет перед созданием нового. Приватная часть ключа живёт только
  на GitHub runner и не сохраняется в репозитории, чате или на сервере.

## Что должно быть настроено один раз

### 1. Сервер

На сервере уже выполнена привязка существующей папки к Git-истории:

```bash
cd /var/www/cvety
git remote get-url origin
git branch --show-current
git rev-parse HEAD
git status --short
```

Ожидаемые первые две строки:

```
https://github.com/cvetofor/sub.git
redesign
```

Если папка разворачивается с нуля, сначала создают сайт и базу по
[`DEPLOY.md`](DEPLOY.md), затем в папке сайта инициализируют Git без
перезаписи уже проверенных файлов:

```bash
git init
git remote add origin https://github.com/cvetofor/sub.git
git fetch --depth=1 origin redesign
git symbolic-ref HEAD refs/heads/redesign
git update-ref refs/heads/redesign refs/remotes/origin/redesign
git read-tree origin/redesign
```

Это записывает историю в `.git`, но не заменяет `.env`, базу данных,
загрузки, `storage/`, `vendor/` или собранные файлы.

### 2. GitHub Secrets

В репозитории: **Settings → Secrets and variables → Actions** должны быть:

| Secret | Назначение |
|---|---|
| `BEGET_LOGIN` | Логин Beget для облачного API |
| `BEGET_PASSWORD` **или** `BEGET_API_PASSWORD` | Пароль для API Beget |
| `SSH_KNOWN_HOSTS` | Проверенный host key VPS для SSH |

Секреты не показывают в задачах, чатах, исходниках и документации. Workflow
останавливается до изменений на VPS, если обязательного секрета нет или API
Beget не выдаёт временный ключ. На аккаунте Beget доступ к API должен быть
включён. При включённой двухфакторной аутентификации API может требовать
отдельный способ авторизации — это проверяется в журнале запуска, а не
обходится паролем через консоль.

Старые `SSH_PRIVATE_KEY`, `SSH_HOST`, `SSH_USER` могут оставаться для
исторического `deploy.yml`, но новый workflow production-выката их не
использует.

### 3. GitHub workflow

Файл `.github/workflows/deploy-production.yml` должен быть в `main`.
Он выполняет следующие защиты:

1. получает указанный `ref` и убеждается, что SHA входит в `redesign`;
2. устанавливает PHP-зависимости, собирает Vite-фронтенд и запускает PHPUnit;
3. получает временный root-ключ через API Beget;
4. загружает готовый `public/build` во временную папку сервера;
5. ставит сайт в режим обслуживания, переключает Git на тот же SHA,
   обновляет зависимости при изменении `composer.lock`, заменяет фронтенд;
6. при явно выбранной опции применяет миграции;
7. пересобирает кэш Laravel, открывает сайт, сверяет SHA и HTTPS-ответ.

Одновременно запускается только один выкат
(`concurrency: cvety-production`). Если команда после `artisan down`
заканчивается с ошибкой, обработчик `trap` пытается выполнить
`artisan up`.

## Как выкатить обычную доработку

1. Создайте ветку от `redesign`, сделайте изменение и откройте PR.
2. Убедитесь, что CI успешен.
3. После проверки влейте изменение в `redesign`.
4. Откройте в GitHub:
   **Actions → «Выкат коммита redesign на production» → Run workflow**.
5. В поле `ref` оставьте `redesign` либо укажите полный SHA проверенного
   коммита.
6. Не включайте «Применить миграции базы данных», если изменение не содержит
   миграций.
7. Дождитесь зелёного статуса всех шагов, особенно:
   «Проверить PHP-код», «Применить тот же коммит на сервере» и
   «Проверить сервер».
8. После зелёного запуска вручную проверьте на сайте именно изменённый
   пользовательский сценарий.

Workflow автоматически проверяет главную по HTTPS с ожидаемым Host и получает
код `200`, но это не заменяет проверку формы, оплаты, личного кабинета или
админки, если они затронуты изменением.

## Миграции и зависимости

Если меняются миграции, запускайте workflow с галочкой
«Применить миграции базы данных». Перед необратимой миграцией необходимо
сделать резервную копию PostgreSQL и описать план отката в PR.

Изменение `composer.lock` workflow распознаёт автоматически и выполняет на
VPS `composer install --no-dev --optimize-autoloader`. Изменение
`package.json`, `package-lock.json`, `vite.config.*` или
`resources/` безопасно: фронтенд всегда собирается на GitHub runner и
загружается как готовый `public/build`; Node.js на VPS не нужен.

## Откат

Для отката в Actions запускают тот же workflow:

1. В поле `ref` указывают полный SHA последнего известного исправного
   коммита из `redesign`.
2. Миграции **не** включают.
3. После зелёного запуска проверяют сайт.

Откат кода не откатывает уже применённые миграции. Если схема базы менялась
необратимо, сначала нужен резервный план восстановления базы.

## Диагностика

| Симптом | Что это значит и что делать |
|---|---|
| PHPUnit сообщает `Vite manifest not found` | Сборка должна идти до тестов. В действующем workflow порядок уже правильный: `npm run build` выполняется перед PHPUnit. |
| `dubious ownership` в Git на VPS | Root и `codex-sub` имеют разных владельцев. Workflow явно добавляет только `/var/www/cvety` как `safe.directory`. Не отключайте защиту Git глобально для всех папок. |
| Нет временного ключа или API Beget вернул ошибку | Проверить наличие `BEGET_LOGIN` и пароля API в Secrets, доступность API и настройки 2FA. Сайт до этого шага не изменяется. |
| Ошибка до «Применить тот же коммит на сервере» | Файлы сайта не изменялись. Исправить workflow/Secrets и повторить запуск. |
| Ошибка во время серверного шага | Посмотреть лог Actions. Workflow пытается вернуть сайт командой `artisan up`; дополнительно проверить HTTPS и `git rev-parse HEAD` ограниченным пользователем. |
| Нужен доступ к серверу | Не использовать веб-консоль и не передавать пароль. Использовать ограниченный SSH-ключ `codex-sub` для аудита либо workflow через API Beget для выката. |

## Проверка текущего состояния

Независимая проверка без изменения данных:

```bash
ssh codex-sub@93.189.231.103 \
  'cd /var/www/cvety && git branch --show-current && git rev-parse HEAD && git status --short'
```

Для HTTP-проверки с самого VPS:

```bash
curl --fail --silent --show-error --max-time 15 \
  --resolve 'xn--b1ag3bn2a.xn--b1ag1aakjpl.xn--p1ai:443:127.0.0.1' \
  https://xn--b1ag3bn2a.xn--b1ag1aakjpl.xn--p1ai/ -o /dev/null -w '%{http_code}\\n'
```

Успешное состояние: ветка `redesign`, нужный SHA, пустой `git status` и
HTTP `200`.

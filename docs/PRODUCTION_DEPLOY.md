# Регламент выката production-сайта

Этот процесс относится к сайту «цветы.цветофор.рф» в `/var/www/cvety`.
Исходная ветка — `redesign`; сервер разворачивает только конкретный коммит
из этой ветки.

## Нормальный порядок

1. Изменение делается в отдельной ветке от `redesign`.
2. После проверки оно попадает в `redesign`.
3. В GitHub Actions вручную запускается «Выкат коммита redesign на production».
   Выбирается `redesign` или полный SHA. Миграции включаются, только если
   они действительно входят в изменение.
4. Workflow заново запускает PHP-тесты, собирает фронтенд и проверяет, что
   выбранный коммит входит в `redesign`.
5. Используя уже настроенные secrets репозитория, workflow загружает сборку на
   VPS, разворачивает тот же SHA, обновляет зависимости при изменении
   `composer.lock` и пересобирает кэш Laravel.
6. После выката workflow сверяет SHA на сервере и HTTPS-ответ главной.
   Затем вручную проверяется затронутый пользовательский сценарий.

## Доступ и секреты

Используются существующие секреты GitHub Actions, уже применяемые старым
workflow `deploy.yml`:

- `SSH_PRIVATE_KEY`;
- `SSH_KNOWN_HOSTS`;
- `SSH_HOST`;
- `SSH_USER`.

Новые ключи, пароль root и консоль Beget не нужны. Приватный ключ и пароль
никогда не попадают в репозиторий, чат или сайт. Проверка host key остаётся
включённой.

## Границы безопасности

- workflow запускается только вручную;
- он отклоняет SHA вне `redesign`;
- миграции базы выполняются только при явно выбранной галочке;
- `.env`, `storage/`, фотографии и данные базы не заменяются;
- одновременно может идти лишь один production-выкат;
- откат — повторный ручной запуск с SHA прежнего проверенного коммита.

Если в старом наборе secrets не окажется SSH-доступа от root, workflow
завершится до выката на проверке подключения и сайт не изменится. В таком
случае доступ настраивается в GitHub/Beget без использования веб-консоли.

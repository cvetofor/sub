# Выкат новой версии сайта (ветка `redesign`)

Документ для того, кто будет выкатывать. Основной сценарий: новый поддомен рядом со старым сайтом
(раздел ниже). Альтернатива с заменой сайта на том же домене описана в конце. Выкат делается один раз и целиком: новая версия меняет маршруты,
вход в кабинет и расчёт платежей, поэтому «половинный» выкат отдельными файлами не подходит.

## Что меняется для бизнеса

- Вход в кабинет по коду из СМС вместо пароля. Старые пароли больше не работают,
  клиенты входят по тому же номеру телефона. Старые подписки находятся по номеру.
- Первый платёж включает подарочный букет: каждую неделю 4 букета по цене 3,
  раз в 2 недели 2 по цене 1, раз в месяц в первый месяц 2 букета по цене 1.
  Повторные списания идут по обычной цене месяца.
- Главная показывается в двух версиях (A/B-тест), результаты в админке: «Подписки пользователей → A/B-тест главной».
- Электронная коммерция Яндекс.Метрики: показы планов, добавление в корзину, покупка.

- Расписание доставок: после оплаты подписка получает даты доставок на месяц, клиент видит их в кабинете
  и может пропустить доставку (букет переносится в конец). Вечером в 18:00 клиенту уходит СМС о завтрашней
  доставке, при неудачном списании тоже СМС. В админке раздел «Доставки» с выгрузкой на день в CSV для флориста.

## Что нужно заранее

| Что | Зачем | Где взять |
|---|---|---|
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | Боевые платежи | Личный кабинет ЮKassa |
| `SMSC_LOGIN`, `SMSC_PASSWORD` | Код входа по СМС | Кабинет SMSC.ru |
| `YM_ID` | Счётчик Метрики с включённой электронной коммерцией (контейнер `dataLayer`) | Яндекс.Метрика → Настройки |
| `APP_ENV=production`, `APP_DEBUG=false` | Без них включается имитация оплаты и код СМС отдаётся в ответе сервера | `.env` на сервере |
| Доступ к базе PostgreSQL | Резервная копия и миграции | Сервер |
| Node 22 и npm на сервере **или** артефакт сборки из CI | Папка `public/build` не хранится в репозитории | GitHub Actions → workflow «CI» → артефакт `public-build` |

Без ключей ЮKassa в production создание подписки вернёт ошибку «Оплата временно недоступна»,
тестовая имитация оплаты в production отключена (отвечает 404).

Важно про `APP_ENV`. В старой версии админка `/hub` работала только при `APP_ENV=local`: модель
пользователя не реализовывала интерфейс Filament, и в режиме `production` панель отвечала 403 всем.
В новой версии это исправлено (`User::canAccessPanel`: только активные сотрудники), поэтому на боевом
сервере ставим `production`. Если сейчас там стоит `local`, менять нужно одновременно с выкатом,
иначе на тестовом стенде с реальными данными любой сможет имитировать оплату и получать код входа без СМС.


## Вариант запуска: новый поддомен рядом со старым сайтом (рекомендуется)

Старый сайт на `подписка.цветофор.рф` продолжает работать как есть. Новая версия поднимается
на соседнем поддомене того же VPS Beget, например `цветы.цветофор.рф`, со своей копией базы.
Ничего в старом сайте не меняется, кроме одного: адрес уведомлений в кабинете ЮKassa переключается
на новый сайт, а новый сайт пересылает старому его уведомления (см. ниже).

### Почему отдельная база, а не общая

| | Отдельная база (копия) | Общая база |
|---|---|---|
| Старый сайт | не трогаем совсем | его база получает новые таблицы и колонки |
| Повторные списания | каждый сайт списывает только свои подписки | два планировщика на одной базе: риск двойного списания, пришлось бы отключать cron старого сайта |
| Админка | две: старая и новая | одна |
| Переезд потом | перенести подписки, оформленные на старом сайте за переходный период (команда импорта, обычно единицы) | ничего переносить не нужно |

Берём отдельную базу: безопаснее для текущих клиентов. Чтобы номера подписок и платежей
на двух сайтах не пересекались, у новой базы сдвигаем счётчики (шаг 5 ниже).

### Автоматически через GitHub Actions

Workflow «Выкат нового сайта на поддомен» (`.github/workflows/deploy-cvety.yml`) делает шаги 2–7 ниже сам:
собирает фронтенд, копирует код в отдельную папку на VPS и запускает `deploy/setup-cvety.sh`.
Скрипт берёт доступы к базе, ЮKassa и SMSC из `.env` старого сайта, создаёт копию базы, применяет миграции,
сдвигает счётчики, настраивает nginx, сертификат и cron. Повторный запуск безопасен.
Доступ к серверу одним из способов (секреты репозитория): `BEGET_LOGIN` + `BEGET_API_PASSWORD` (пароль API из
https://cp.beget.com/settings/security/api; тогда workflow сам добавит SSH-ключ на сервер и DNS-запись через API Beget;
если для входа в облачное API нужен пароль аккаунта, добавить его как `BEGET_PASSWORD`), либо готовый `SSH_PRIVATE_KEY`,
либо `SSH_PASSWORD` (пароль root),
по желанию `CVETY_EXTRA_ENV` со строками `YM_ID=…`, `TELEGRAM_BOT_TOKEN=…`, `TELEGRAM_CHAT_ID=…`.
IP, пользователь и папки задаются при запуске; папка старого сайта находится автоматически по его `.env`.
Workflow запускается вручную, для этого его файл должен лежать в ветке `main` (ограничение GitHub).
Вручную остаются только DNS-запись (шаг 1) и переключение адреса уведомлений ЮKassa (шаг 8).

### Шаги на VPS Beget (вручную, если без Actions)

1. **DNS.** В панели Beget у домена `цветофор.рф` добавить A-запись `цветы` → IP VPS
   (тот же, что у `подписка`). Для кириллического имени панель сама покажет punycode:
   `xn--b1ag3bn2a.xn--b1ag1aakjpl.xn--p1ai`.
2. **Папка и код.**
   ```bash
   sudo -u www-data git clone -b redesign https://github.com/cvetofor/sub /var/www/cvety
   cd /var/www/cvety && composer install --no-dev --optimize-autoloader
   ```
   Фронтенд: `npm ci && npm run build` на сервере (Node 22) либо распаковать артефакт `public-build`
   из GitHub Actions в `public/build`.
3. **База.** Копия боевой базы в новую:
   ```bash
   sudo -u postgres createdb cvety_sub
   pg_dump cvetofor_sub | sudo -u postgres psql cvety_sub
   ```
4. **`.env`** (на основе `.env.example`):
   ```
   APP_ENV=production
   APP_DEBUG=false
   APP_URL=https://xn--b1ag3bn2a.xn--b1ag1aakjpl.xn--p1ai
   SITE_HOST=цветы.цветофор.рф
   DB_DATABASE=cvety_sub
   YOOKASSA_SHOP_ID=…  YOOKASSA_SECRET_KEY=…
   YOOKASSA_LEGACY_CALLBACK=https://xn--80ahmirfcr.xn--b1ag1aakjpl.xn--p1ai/api/payment/yookassa/callback
   SMSC_LOGIN=…  SMSC_PASSWORD=…
   YM_ID=…
   TELEGRAM_BOT_TOKEN=…  TELEGRAM_CHAT_ID=…
   ```
   `php artisan key:generate` только если ключа нет; сессии и cookie у сайтов разные, это нормально.
5. **Миграции и сдвиг счётчиков.**
   ```bash
   php artisan migrate --force
   sudo -u postgres psql cvety_sub -c "ALTER SEQUENCE subscriptions_id_seq RESTART WITH 100000; ALTER SEQUENCE payments_id_seq RESTART WITH 100000; ALTER SEQUENCE users_id_seq RESTART WITH 100000; ALTER SEQUENCE plans_id_seq RESTART WITH 100000;"
   php artisan deliveries:backfill
   php artisan config:cache && php artisan route:cache && php artisan view:cache && php artisan filament:optimize
   ```
6. **nginx.** Отдельный server-блок (пример в `docs/nginx-cvety.conf`), корень `/var/www/cvety/public`,
   тот же php-fpm, что у старого сайта. Сертификат:
   ```bash
   sudo certbot --nginx -d xn--b1ag3bn2a.xn--b1ag1aakjpl.xn--p1ai
   ```
7. **Cron.** Вторая строка рядом со строкой старого сайта:
   ```
   * * * * * cd /var/www/cvety && php artisan schedule:run >> /dev/null 2>&1
   ```
8. **ЮKassa.** В кабинете магазина адрес HTTP-уведомлений поменять на
   `https://xn--b1ag3bn2a.xn--b1ag1aakjpl.xn--p1ai/api/payment/yookassa/callback`.
   Платежи нового сайта помечены в metadata `site=v2`; уведомления без метки новый сайт
   пересылает на `YOOKASSA_LEGACY_CALLBACK`, то есть старому сайту, и он работает как раньше.
   Пока адрес не переключён, оплаты на новом сайте не подтвердятся: клиент увидит страницу
   «Проверяем оплату». Поэтому переключать адрес в момент открытия нового сайта.

### Переходный период и переезд

- Оба сайта работают параллельно. Новые клиенты идут на новый поддомен, реклама ведёт туда же.
- Когда решим закрыть старый: на `подписка.цветофор.рф` ставим редирект 301 на новый поддомен,
  подписки, оформленные на старом сайте за это время, переносим командой импорта (напишем к тому моменту,
  обычно это единицы записей), `YOOKASSA_LEGACY_CALLBACK` очищаем.
- Если захотим вернуть всё на `подписка.цветофор.рф`: меняем `APP_URL`, `SITE_HOST`, server_name в nginx и сертификат; код не меняется.

## Порядок выката на тот же домен (альтернатива)

1. **Резервная копия базы.**
   ```bash
   pg_dump -Fc cvetofor_sub > backup-$(date +%F).dump
   ```
2. **Режим обслуживания** (2–3 минуты).
   ```bash
   php artisan down --retry=60
   ```
3. **Код.** Получить ветку `redesign` целиком (не отдельные файлы):
   ```bash
   git fetch origin redesign && git checkout redesign && git pull
   composer install --no-dev --optimize-autoloader
   ```
4. **Фронтенд.** Либо собрать на сервере, либо распаковать артефакт CI в `public/build`:
   ```bash
   npm ci && npm run build
   ```
5. **Переменные окружения.** Добавить в `.env` значения из таблицы выше. Проверить `APP_URL=https://подписка.цветофор.рф`.
6. **Миграции.** Они безопасны для существующих данных: только добавляют колонки, делают
   три колонки подписок необязательными и дописывают `phone_e164` существующим пользователям.
   ```bash
   php artisan migrate --force
   ```
7. **Кэши.**
   ```bash
   php artisan config:cache && php artisan route:cache && php artisan view:cache
   php artisan filament:optimize
   ```
8. **Планировщик.** Убедиться, что в cron есть строка. По расписанию работают: повторные списания раз в 2 часа,
   СМС-напоминания о доставках в 18:00, закрытие прошедших доставок в 02:00. Для существующих оплаченных подписок
   расписание создаётся командой `php artisan deliveries:backfill` один раз после миграций.
   ```
   * * * * * cd /path/to/site && php artisan schedule:run >> /dev/null 2>&1
   ```
9. **Вебхук ЮKassa.** Адрес не изменился: `POST /api/payment/yookassa/callback`. Событие `payment.succeeded`.
10. **Открыть сайт.**
    ```bash
    php artisan up
    ```

## Проверка после выката (10 минут)

- Главная открывается, в DevTools → Application → Cookies есть `ab_hero` и `ab_visitor`.
- `/subscribe?plan=1` открывает мастер, шаги 1–4 проходят, код из СМС приходит на реальный номер.
- Тестовый платёж на 1 ₽ через боевой ЮKassa не делаем: вместо этого оформить подписку с минимальным планом и сразу отменить её в кабинете ЮKassa, либо проверить на тестовом магазине ЮKassa с тестовыми ключами на стенде.
- В админке `/hub/subscriptions` появилась подписка со статусом, днём доставки и пожеланиями.
- В админке «A/B-тест главной» растут счётчики «Открыли главную».
- В Метрике: Отчёты → Электронная коммерция → появились показы товаров.
- `/sitemap.xml` отвечает XML, `/robots.txt` закрывает мастер, кабинет и оплату.

## Откат

1. `php artisan down`
2. `git checkout main && composer install --no-dev`
3. Восстановить базу из резервной копии: `pg_restore -c -d cvetofor_sub backup-*.dump`
   (откат миграций командой `migrate:rollback` возможен, но восстановление копии надёжнее:
   новые подписки могли быть созданы с `user_id`, которого нет на старой версии).
4. `php artisan config:cache && php artisan up`

## Чего намеренно нет в выкате

- Старый workflow `deploy.yml` синхронизирует только изменённые файлы по rsync. Для этого выката он не подходит:
  нужна полная выкладка ветки и сборка фронтенда. Его можно оставить для последующих мелких правок,
  добавив в него шаг сборки `npm run build` и синхронизацию `public/build`.
- Фотографии в `public/images/site` пока референсы. После съёмки они заменяются файлами с теми же именами,
  код менять не нужно.

## Решение по A/B-тесту

Главная метрика: доля посетителей, дошедших до шага 3 мастера. Решение принимается
не раньше 14 дней и не меньше 300 стартов мастера на каждую версию. Победившая версия
закрепляется константой `VARIANTS` в `app/Http/Middleware/AssignHeroVariant.php`
(оставить одно значение), второй шаблон героя можно удалить.

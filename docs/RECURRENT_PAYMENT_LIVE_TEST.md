# Проверка рекуррентного платежа на production

Этот сценарий проверяет настоящее повторное списание в ЮKassa. Он не является
тестом «в песочнице»: деньги могут быть списаны с карты. Используйте его только
для собственной подписки руководителя и только после явного подтверждения суммы
и номера подписки.

## Что проверяем

После первого оплаченного месяца сайт сохраняет у ЮKassa идентификатор способа
оплаты. Затем ЮKassa может списать следующий месяц без повторного ввода карты.
Проверка должна подтвердить всю цепочку:

1. первый платёж прошёл и способ оплаты сохранён;
2. создано ровно одно повторное списание;
3. сайт получил ответ или уведомление ЮKassa;
4. подписка продлена, а для следующего месяца созданы доставки и отправлено
   стандартное СМС.

## Перед началом

- В личном кабинете ЮKassa для магазина должны быть подключены автоплатежи.
- Клиент должен дать согласие на регулярные списания в условиях подписки.
- Создайте новую **собственную** подписку через обычный интерфейс сайта и
  самостоятельно оплатите первый месяц. Не используйте данные клиента и не
  создавайте фиктивные покупки.
- Дождитесь уведомления о первой оплате: подписка должна стать активной.
- Не запускайте общее расписание `subscriptions:charge-recurrent`: оно работает
  со всеми подписками, срок которых наступил.

## Бюджет после завершения проверки

Контрольная проверка завершена успешно. Нижний порог «Своего бюджета» в квизе
возвращён к обычным **990 ₽** одновременно в серверной проверке, интерфейсе и
автоматическом тесте. Готовые тарифы и старый мастер оформления не менялись.

## Безденежная проверка готовности

Подключитесь как `codex-deploy` и выполните команду, заменив `123` на номер
своей подписки:

```bash
cd /var/www/cvety
sudo -u www-data php artisan subscriptions:charge-one-recurrent 123
```

Команда ничего не списывает. Она выводит только технические признаки:

- `monthly_amount` — сумма следующего месяца;
- `active=yes` — подписка активна;
- `saved_payment_method=yes` — после первого платежа доступен способ оплаты;
- `next_payment_date` — дата, которая будет дополнительной защитой от
  повторного запуска.

Если хотя бы один из первых трёх признаков не подходит, оплату не запускают:
сначала разбирают первую оплату и журнал сайта.

## Единственное реальное списание

Перед этим шагом ответственный должен отдельно подтвердить в чате:

> Списать по подписке №123 сумму 1 990 ₽ за период с датой следующей оплаты
> 2026-12-01.

Только после такого подтверждения выполняют:

```bash
cd /var/www/cvety
sudo -u www-data php artisan subscriptions:charge-one-recurrent 123 \
  --due=2026-12-01 --confirm=123
```

Два повторённых значения — не формальность:

- `--confirm=123` не даёт отправить платёж без повторения номера подписки;
- `--due=2026-12-01` не даёт случайно повторить ту же команду после успешного
  продления: дата следующей оплаты уже изменится.

Команда обращается только к указанной подписке. Она не запускает общий
планировщик и не выбирает других клиентов.

## Ожидаемый результат и проверка

Варианты результата:

| Сообщение | Значение | Что делать |
|---|---|---|
| `Платёж создан и ожидает ответ банка` | ЮKassa приняла запрос, но банк ещё отвечает | Дождаться webhook от ЮKassa и проверить подписку повторно. Не запускать команду второй раз. |
| `Платёж успешно списан, подписка продлена` | Списание и обработка ответа произошли сразу | Проверить новый платёж, новую дату оплаты, созданные доставки и СМС. |
| `Банк не подтвердил повторное списание` | Списание не прошло, подписка поставлена на паузу по обычному правилу сайта | Не повторять запрос. Проверить причину в ЮKassa; возобновлять после решения владельца подписки. |

Если журнал содержит `Receipt is missing or illegal`, это ошибка формирования
запроса сайта, а не отказ банка и не проблема карты. Повторно списывать до
выката исправления нельзя: сначала убедитесь, что повторный платёж передаёт
чек с названием подписки, суммой и телефоном плательщика.

Если ЮKassa вернула ошибку до создания платежа, но при исправлении запроса
сообщает, что прежний `Idempotence-Key` уже использован, ключ можно заменить
**только вручную и только после отдельного подтверждения владельца**. Для этого
к обычной адресной команде добавляют `--replace-rejected-key`. Опция не
используется автоматическим расписанием и не подходит для сетевой ошибки или
статуса `pending`: в этих случаях прежний ключ сохраняют, чтобы исключить
двойное списание.

После проверки фиксируют в журнале проекта: номер подписки без ФИО и телефона,
сумму, дату, ID операции ЮKassa (если есть), результат, время webhook и
результат проверки кабинета. Номера карт, токены, пароли и персональные данные
в GitHub, журнал или чат не попадают.

## Важные ограничения

- Успешное боевое списание запускает обычные последствия: продлевает подписку,
  планирует доставки следующего месяца и отправляет СМС. Это нужно учитывать
  при выборе собственной тестовой подписки.
- Не используйте команду для повторного списания той же даты. Для возврата
  денег применяется отдельный согласованный процесс возврата в ЮKassa, а не
  второй запуск или ручная правка базы.
- Команда предназначена для разовой контролируемой проверки. Регулярные
  списания продолжает выполнять расписание сайта каждые два часа.
